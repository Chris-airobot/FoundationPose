# RBY1 FoundationPose handoff — 2026-09-03

This file freezes the exact state reached during the first RBY1 right-D405 -> FoundationPose integration session so the next session can resume without repeating camera/calibration debugging.

## Goal

Use the RBY1 right-hand Intel RealSense D405 for live RGB-D FoundationPose inference on the physical cuboid, then convert the returned camera-frame object pose into the robot base frame using the completed hand-eye calibration.

Target pipeline:

```text
right D405 -> aligned RGB-D -> FoundationPose -> camera_T_object
                                      |
                              base_T_camera from TF
                                      |
                               base_T_object
```

## Important intrinsics discrepancy to verify next session

The old Iris/color calibration used the following 640x480 color intrinsics:

```text

fy = 391.809020996094
cx = 323.359405517578
cy = 241.145553588867
```

The direct local librealsense path used for the verified aligned capture/live publisher reported at runtime:

```text
fx = 434.641174
fy = 434.212646
cx = 323.722992
cy = 241.269516
```

Do **not** silently mix these two intrinsics sets. Before trusting the final `base_T_object`, confirm why the direct SDK profile differs from the prior Iris profile and use the exact K corresponding to the RGB image that FoundationPose receives.

The direct aligned SDK capture itself is internally consistent because it saves the runtime K from the same color stream used for RGB and alignment.

## Camera ownership rules

The right D405 can only be owned by one process at a time.

Before custom capture/live publisher:

```bash
sudo systemctl stop rs-right-iris.service
```

After finishing custom D405 work:

```bash
sudo systemctl start rs-right-iris.service
```

Do not stop the left-hand camera service.

## Paths that were tested and should NOT be repeated

### Iris depth publishing

`rs-right-iris.service` can generate depth internally but its configured depth ROS branch did not create the expected ROS publisher and queues filled. Do not spend another session debugging this unless required for production integration.

### Official `realsense2_camera`

Installed packages on Nvidia:

```text
ros-humble-librealsense2      2.58.3
ros-humble-realsense2-camera  4.58.3
```

The official ROS node repeatedly reported:

```text
No RealSense devices were found!
```

while the local `/usr/local` librealsense/GStreamer stack could access the D405. Do not use the official wrapper for this POC.

### Python pyrealsense2 on Nvidia

The local Python installation is incomplete. The directory exists but only contains `pyrsutils`; importing `pyrealsense2` gives an empty namespace package with no `context` attribute. Do not rebuild librealsense just to obtain Python bindings.

### Direct TCP RGB-D server

An experimental direct TCP server was attempted after the live ROS2 publisher. Its first run failed at `pipe.start()` with:

```text
rs2::error: No device connected
```

It was not validated and is intentionally not committed as the recommended path.

## Samsung `.155` ROS note
